1. Prepare o backend que as rotas vão usar

DynamoDB e filas FIFO

  1. Em DynamoDB → Tables → Create table, crie uma tabela On-demand. Use pk como partition key e sk como sort key, ambas String. Em Additional settings → Time to Live, habilite o atributo ttl.
  2. Crie primeiro uma DLQ FIFO e depois a fila principal FIFO em SQS → Queues → Create queue. Use nomes terminados em .fifo e criptografia SSE-SQS. Na fila principal, ligue High throughput FIFO para usar deduplicação e throughput por grupo. Desabilite a deduplicação por conteúdo porque o Gateway envia o ID explicitamente. Configure redrive para a DLQ após 20 recebimentos, valor escolhido no laboratório para dar margem a falhas transitórias durante os testes.
  3. Na fila principal, em Edit → Configuration → Visibility timeout, configure 180 segundos.

O padrão do SQS é 30 s. Neste laboratório, o timeout da Processor é 30 s e o gatilho FIFO não usa janela de batching. A AWS recomenda pelo menos seis vezes o timeout da função consumidora para dar margem a novas tentativas em caso de throttling. Por isso, configure 6 × 30 s = 180 s na fila principal. Esse tempo começa quando a mensagem é recebida. Se o processamento terminar com sucesso, a mensagem é removida imediatamente. Se ela não for removida, pode voltar a ficar disponível ao expirar a visibilidade. Padrão do SQS · Recomendação da AWS para Lambda com SQS

Compile e empacote as Lambdas

Na raiz do laboratório, instale as dependências, compile o TypeScript e remova as dependências de desenvolvimento antes de entrar em backend/dist.

cd backend &&
  npm ci &&
  npm run build &&
  npm prune --omit=dev &&
  cd dist

Já em backend/dist, execute os três comandos abaixo no macOS. Os ZIPs são criados na própria dist.

/usr/bin/tar -a -cf lambda-controller.zip lambda-controller shared -C .. package.json node_modules
/usr/bin/tar -a -cf lambda-generator.zip lambda-generator shared -C .. package.json node_modules
/usr/bin/tar -a -cf lambda-processor.zip lambda-processor shared -C .. package.json node_modules

O -a seleciona o formato pela extensão .zip. O tar lê a pasta da função e shared/ na dist. Depois, -C .. muda o diretório de leitura para backend e adiciona package.json e node_modules/ na raiz do ZIP.

Antes de enviar o ZIP, confirme que o tar terminou sem erros e que o pacote contém o arquivo de entrada e as dependências. Para a Controller, o comando deve mostrar as quatro entradas abaixo.

unzip -Z1 lambda-controller.zip | grep -Ex 'lambda-controller/control\.js|shared/db\.js|package\.json|node_modules/'

Crie as funções e o gatilho

Em Lambda → Create function → Author from scratch, crie as três funções com Node.js 22. Em Code → Upload from → .zip file, envie o ZIP correspondente: lambda-controller.zip, lambda-generator.zip ou lambda-processor.zip. Em Runtime settings → Edit, escolha o handler de cada função.

Para a Controller, envie lambda-controller.zip e configure lambda-controller/control.handler em Runtime settings → Edit antes de testar. O prefixo lambda-controller/ corresponde à pasta do control.js dentro do ZIP.

Crie as roles em IAM → Roles com confiança para lambda.amazonaws.com. Anexe AWSLambdaBasicExecutionRole a cada role para o CloudWatch Logs e acrescente as ações abaixo nos recursos correspondentes. Escolha a role da função ao criá-la.

Ative o reporte de falhas parciais do SQS

Em Lambda → Processor → Configuration → Triggers, adicione ou edite o gatilho da fila principal FIFO. Defina Batch size = 10, marque Report batch item failures e salve. A opção corresponde a ReportBatchItemFailures na API da AWS.

A Processor devolve os IDs das mensagens com falha em batchItemFailures. Em FIFO, ela também inclui as mensagens seguintes que ainda não processou, para preservar a ordem. O gatilho remove as mensagens concluídas e as demais voltam a ficar disponíveis após o visibility timeout. Sem essa opção, uma resposta normal da função pode fazer o gatilho remover o lote inteiro, inclusive pedidos que falharam no DynamoDB. Documentação da AWS

{

As expressões que fazem a tradução: no individual, $input.body lê o JSON inteiro e $util.urlEncode(...) prepara os valores para o formulário. $input.path("$.runId") e $input.path("$.shard") formam o MessageGroupId; orderId vira MessageDeduplicationId. No lote, #foreach($order in $input.path('$.orders')) cria uma entrada por pedido, e $util.escapeJavaScript($input.json($path)) prepara o JSON daquele pedido para ir como texto dentro de MessageBody. O replaceAll corrige o escape das aspas simples para manter o JSON válido.

3. Templates em Integration response

O Gateway recebe o status e o corpo HTTP do SQS, seleciona o template e devolve o status e o corpo da nossa API.

  • Individual: o SendMessage responde com HTTP 200 e XML, que traz campos como MessageId e SequenceNumber no caso da FIFO. O template produz {"accepted": true} e o Gateway devolve HTTP 202. Resposta de SendMessage
  • Lote: o SendMessageBatch responde com HTTP 200 e JSON com Successful e Failed. O VTL $input.body repassa o corpo e o Gateway mantém HTTP 200, inclusive se alguns itens falharem. Resposta de SendMessageBatch

Em Method response, crie 202 para o envio individual ou 200 para lote, mais 400, 429 e 500. Declare o header Access-Control-Allow-Origin nas respostas. Em Integration response, associe o valor estático '*' a esse header em cada resposta, incluindo a resposta padrão. Mapeie o sucesso individual para {"accepted":true} e o sucesso em lote para $input.body. Use seleção por status 4\d{2} e 5\d{2} para mapear para 400 e 500. Use os templates completos de resposta de cada rota. Os templates de erro convertem RequestThrottled em 429 e incluem source=SQS. Preserve as listas Successful e Failed em HTTP 200 para a geradora contar o resultado de cada pedido. Contrato de SendMessageBatch

O que é um shard neste laboratório?

Um shard é uma parte do estoque de uma execução. A Lambda Control cria um item no DynamoDB por shard, com saldo próprio. O API Gateway usa o ID da execução e o número do shard para montar o grupo FIFO no SQS. Assim, pedidos do mesmo shard seguem em ordem, enquanto grupos diferentes podem avançar em paralelo e atualizar itens diferentes do estoque.

O roteiro usa 1.024 shards em todas as linhas para comparar os volumes com a mesma configuração do teste de 1 milhão. Com mais shards, as atualizações se distribuem entre mais itens do DynamoDB e há mais grupos FIFO disponíveis para processamento em paralelo.

O código do laboratório usa 1.024 shards e lotes de até 10 pedidos. O painel e as Lambdas usam os mesmos valores ao calcular o envio.

Como os shards entram na conta dos workers

Com 100 mil pedidos, estoque inicial de 100 mil e 1.024 shards, 672 shards recebem 98 pedidos e 98 unidades de estoque, e 352 recebem 97 de cada. Cada shard precisa de 10 lotes de até 10 pedidos, somando 10.240 chamadas HTTP. A sugestão de workers usa esse total e a referência do benchmark (⌈50 × 10.240 ÷ 100.352⌉ = 6).

A tabela mostra uma referência proporcional ao benchmark. Para executar a carga pelo painel, o cálculo automático usa 30 chamadas HTTP/s por worker e chega a 56 workers para 1 milhão de pedidos em lote em 60 s.

Mantenha os lotes de até 10 no envio e no consumo e 1.024 shards. A processadora usa 96 unidades de escrita/s por invocação, definidas no código. Para 100 mil pedidos, a concorrência resulta de ⌈128 × 100.000 ÷ 1.000.000⌉ = 13. O warm write proporcional seria 1.600, então o roteiro mantém 4.000 como ponto de partida para uma tabela nova. O Rate proporcional seria 2.000, e o perfil inicial mantém 2.500. O rate efetivo também depende da quota regional e do tráfego de outras APIs.

No modo individual, 100 mil pedidos em 60 s sugerem 56 workers. A partir de 200 mil na mesma janela, a sugestão passa do limite de 100 workers do laboratório. Aumente a janela ou use envio em lote.

Como funcionam rate e burst no API Gateway

O Rate é o ritmo de reposição dos créditos, em chamadas HTTP por segundo. O Burst é a capacidade máxima do balde de créditos para absorver uma rajada curta. Cada chamada consome um crédito. Com Rate de 2.500 req/s e Burst de 500, o balde cheio tem 500 créditos disponíveis imediatamente e é reabastecido a 2.500 por segundo. Se chegar mais tráfego quando os créditos acabarem, o Gateway pode devolver HTTP 429. Os valores do usage plan são aplicados em regime de melhor esforço e também estão sujeitos aos limites do stage e da conta na região. Throttling e token bucket na AWS

O perfil inicial usa Burst 500 porque adotamos 20% do Rate de 2.500 como ponto de partida. Nos demais perfis em lote da tabela, parta do Burst 5.000 do benchmark e use 500 créditos por 100 mil pedidos, respeitando a capacidade de rajada disponível na conta.
